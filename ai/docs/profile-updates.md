# 개인·집단 프로필 갱신

`profile_updates.update_profile(state, request)`는 새 상태를 반환하는 순수 함수다.
기존 객체를 수정하지 않으며 실패 배치에는 부분 반영 상태를 반환하지 않는다.
호출자는 `expected_state_version`과 `expected_profile_reference`를 모두 전달한다.
하나라도 다르면 VERSION_MISMATCH로 거부한다. 성공 후 DB에 저장할 때 같은 기대
버전으로 원자적 비교·교환(CAS)을 수행하는 책임은 BE에 있다.

## 갱신 흐름

1. 기대 버전·기준 시점·사용자/집단·통화·원천을 확인한다.
2. `changes_complete_from`부터 `changes_complete_until`까지 변경 이력이 완전하다는
   호출자의 선언이 이전 기준 시점부터 새 기준 시점까지를 덮는지 확인한다.
3. 구매별 수정 사건을 복사된 상태에 적용한다.
4. 현재까지 알려진 표본의 학습 기준 시점을 새 시점으로 옮긴다. 확인되지 않은 구매를
   자동으로 정상 확정하지 않는다. 확인 변경에는 새로운 완전한 표본이 필요하다.
5. 기존 개인/집단 생성기로 최근·장기 분포를 재계산하고 기간 밖 표본을 제거한다.
6. 프로필 내용 버전과 수정 상태 버전, 이전 버전, 사건별 처리 결과·이유를 반환한다.

중앙값·분위수·원형 시간 분포·USER_EQUAL 가중치는 보관 중인 표본으로 정확히
재계산한다. 계산량은 보관 표본 수에 비례하며 상수 시간 온라인 평균 갱신이 아니다.
같은 기준 시점·메타데이터·입력으로 재전달하면 UNCHANGED가 된다. 새 영수증만
추가되면 상태 버전은 바뀌어도 프로필 버전은 유지된다. 기준 시점이나 생성/만료
메타데이터가 바뀌면 다른 프로필 내용이다. 버전 문자열은 증가하는 번호가 아니다.

## 전체 재생이 필요한 상황

- 변경 이력의 기간이 빠짐: CHANGE_HISTORY_GAP
- 새 장기 기간이 기존 보관 범위를 넘어섬: RETENTION_GAP
- 집단 명세/구성원 변경: COHORT_CHANGED
- 구매 수정 번호가 중간에서 빠짐: MISSING_REVISION
- 초기 통계에 현재 평가 구매가 이미 포함됨: CURRENT_PURCHASE_IN_STATE

기간 확대라도 새 시작 시점이 기존 보관 범위 안이면 처리할 수 있다. 집단 구성원
목록의 순서 변경은 의미 변경으로 보지 않는다. REPLAY_REQUIRED일 때는 완전한
원천 이력으로 기존 생성기를 다시 실행하고 `initialize_profile_update`로 새 상태를
만들어야 한다. DB 변경·재학습 스케줄·오염 방지 추가 정책은 이 함수의 범위가 아니다.

원시 사건 정정이 다른 구매의 빈도 피처에도 영향을 준다면 해당 구매들의 수정도
함께 전달해야 한다. 한 구매만 바꾸고 파생 피처의 누락을 알아서 추론하지 않는다.
완전성 선언의 진실 여부는 이 함수만으로 입증할 수 없다.

`ProfileUpdateState.model_validate_json(...)`으로 보관 상태를 복원한다.
상태에는 중앙값·분위수 계산에 필요한 원표본과 중복/정정 정보가 모두 들어 있다.

검증: `python -m pytest tests/learning/updates/test_profile_updates.py -v --tb=short`
