# 전체 학습 재생과 갱신 결과 비교

`profile_update_replay.replay_profile_update(state, request, samples)`는 새 기준 시점의
**완전한 학습 표본**과 기존 보관 상태의 차이를 구매 수정 사건으로 만든다.
일부 새 사건만 담긴 목록을 넣으면 누락된 기존 구매를 삭제로 해석하므로, 이 입력에
부분 배치를 사용하면 안 된다. 부분 배치는 `update_profile`의 명시적 사건 API를 쓴다.

입력은 기존 학습 재생기가 만든 LearningSample이며 기준 시점·출처가 동일해야 한다.
대상 사용자/집단·통화에 해당하는 보관 기간 표본만 선택한다. 현재 평가 구매와
충돌하는 구매 중복을 허용하지 않는다. 원천 데이터의 정답 라벨·페르소나는 읽지 않는다.

변경은 금액, 확인 결과, 주문 버전뿐 아니라 원시 피처·결측·수집 범위에도 적용한다.
따라서 한 원시 사건의 정정으로 후속 구매의 빈도 피처가 달라졌다면, 완전한 재생
결과에서 해당 후속 구매도 찾아 교체한다. 자연스럽게 기간 밖으로 밀려난 구매는
삭제 수정 사건을 만들지 않고 통계 기간에서 제거한다.

생성 사건의 이유는 REPLAY_DIFF이고 `available_at`은 전체 차이를 확인한 새 기준
시점이다. 원래 피드백의 발생 순서를 복원한 사건 기록이 아니다. 수정 번호와 사건 ID는
이 상태의 차이를 재현하기 위한 번호다. 원본 수정 체인을 사용하는 호출과 섞으려면
상위 호출자가 번호 체계와 책임을 일관되게 관리해야 한다.

성공 후 별도로 **최종 전체 표본을 기존 개인/집단 생성기에 직접 입력**해 비교한다.
이 비교는 갱신 함수에 같은 사건 목록을 두 번 넣는 검사가 아니다. 최근·장기 통계,
보관 표본, 피처 결측, 구성원 기여, 프로필 메타데이터를 비교하며 `matched`와 두 내용
해시를 반환한다. 수정 영수증은 전체 재생에 존재하지 않으므로 비교 대상에서 제외한다.
`compare_profile_replay`는 기존 갱신 결과를 독립적으로 비교하는 용도로도 사용할 수 있다.

이 결과는 상태 갱신의 재현성과 통계 일관성 검증이다. 사기 탐지 정확도나 실제 트래픽
성능 측정은 아니다. 완전한 원천이 없는 경우 잘못된 완전성 선언 자체를 탐지할 수 없다.

검증: `python -m pytest tests/learning/updates/test_replay.py -v --tb=short`
