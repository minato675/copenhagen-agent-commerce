# Review Convention

본 문서는 Merge Request의 리뷰 필요 여부 판단 기준과 Reviewer 선정 기준을 정의한다.

MR 작성 및 병합에 관한 세부 규칙은 `mr-convention.md`를 따른다.

---

## 1. 기본 원칙

모든 MR이 리뷰를 필요로 하지는 않는다.

리뷰 필요 여부는 작업의 난이도나 변경량이 아니라 **변경이 다른 팀원의 작업에 영향을 주는지**를 기준으로 판단한다.

```text
변경이 내 담당 영역 안에서 끝나는가?
        │
        ├── 예   → Self Merge
        │
        └── 아니오 → Reviewer 지정
```

판단이 애매한 경우에는 Reviewer를 지정한다.

---

## 2. Reviewer가 필요한 경우

다음 중 하나에 해당하면 Reviewer를 최소 1명 지정한다.

| 구분 | 예시 |
| --- | --- |
| 공유 계약 변경 | `backend/libs/ucp-contract`, `payment-handler-contract`, `internal-api-contract`의 요청/응답 구조 변경 |
| 서비스 간 API 변경 | 다른 서비스가 호출하는 엔드포인트의 경로, 파라미터, 응답, 에러 코드 변경 |
| 공통 모듈 변경 | 여러 모듈이 함께 사용하는 라이브러리, 공통 설정, `test-support` 변경 |
| DB schema 변경 | Flyway migration 추가, 테이블·컬럼 변경, 소유권이 걸린 데이터 구조 변경 |
| 서비스 경계 변경 | 책임 서비스 이동, 호출 방향 변경, 새로운 서비스 간 의존 추가 |
| 여러 파트에 걸친 변경 | Backend와 Frontend, Mobile, AI 중 둘 이상의 작업 공간을 함께 변경 |
| 팀 규칙 변경 | 컨벤션 문서, ADR, 팀 전체가 따라야 하는 가이드 변경 |

해당 MR은 Reviewer의 리뷰가 완료된 후 병합한다.

---

## 3. Self Merge가 가능한 경우

다음 조건을 **모두** 만족하면 Reviewer를 지정하지 않고 Self Merge할 수 있다.

- 변경 범위가 본인 담당 영역 안에서 끝난다.
- 다른 팀원이 사용하는 계약, 공통 모듈, DB schema를 변경하지 않는다.
- 서비스 경계나 호출 방향을 바꾸지 않는다.

예시:

```text
담당 서비스 내부의 비즈니스 로직 구현
담당 서비스 내부 리팩터링
본인이 작성한 코드의 테스트 추가
본인 담당 영역의 문서 및 오타 수정
```

Self Merge를 하더라도 `mr-convention.md`의 MR 제목, 본문, Draft 해제 전 확인 항목은 동일하게 지킨다.

리뷰를 받지 않는 대신 MR 본문에 변경 내용과 검증 방법을 남겨 다른 팀원이 나중에 변경 이력을 추적할 수 있도록 한다.

---

## 4. Reviewer 선정 기준

Reviewer는 **변경의 영향을 받는 영역의 담당자**로 지정한다.

| 변경 내용 | Reviewer |
| --- | --- |
| 공유 계약 변경 | 해당 계약을 사용하는 서비스의 담당자 |
| 서비스 간 API 변경 | 해당 API를 호출하는 쪽의 담당자 |
| 공통 모듈 변경 | 해당 모듈을 사용하는 서비스의 담당자 중 1명 |
| DB schema 변경 | 해당 DB를 소유한 서비스의 담당자 |
| 여러 파트에 걸친 변경 | 영향을 받는 각 파트에서 1명씩 |
| 팀 규칙 변경 | 해당 규칙을 함께 정한 팀원 |

모듈별 담당 영역은 `CONTRIBUTING.md`의 작업 위치 표를 기준으로 확인한다.

담당자가 명확하지 않거나 영향 범위를 판단하기 어려운 경우에는 코드를 작성하기 전에 팀과 논의하고, 필요하면 `docs/adr/`에 결정을 기록한다.

---

## 5. Reviewer 수

Reviewer는 필요한 최소 인원만 지정한다.

- 하나의 영역에만 영향을 주는 경우: 1명
- 여러 파트에 영향을 주는 경우: 영향을 받는 파트마다 1명

리뷰가 필요하지 않은 팀원을 참고 목적으로 Reviewer에 추가하지 않는다. 공유가 목적이라면 Reviewer 지정 대신 MR 링크를 팀 채널에 공유한다.

---

## 6. Reviewer 지정 시점

Reviewer는 Draft를 해제하여 정식 MR로 전환하는 시점에 지정한다.

---

## 7. 리뷰 진행

리뷰 과정에서 수정이 필요한 경우 기존 작업 브랜치에서 수정한 뒤 다시 Push한다. MR을 새로 생성하지 않는다.

Reviewer가 지정된 MR은 다음 조건을 만족한 후 병합한다.

- Reviewer의 리뷰가 완료된 상태

병합 조건의 나머지 항목은 `mr-convention.md`를 따른다.
