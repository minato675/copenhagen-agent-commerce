# 용어 정의 (Glossary)
> [v0.2]

## 1. CP0 
- 본 프로젝트의 확정 명칭. AI가 상품 탐색부터 구매, 결제까지 수행하는 결제 에이전트 서비스

## 2. MCP (Model Context Protocol)
Anthropic이 2024년 11월 공개한 오픈 프로토콜

### 2.1. Primitives (기본 구성 요소)
**tools** — 모델이 호출해 부작용(side effect)을 일으키는 실행형 기능. 제어 주체는 model.
**resources** — 모델에게 컨텍스트로 제공되는 읽기 전용 데이터. 제어 주체는 application.
**prompts** — 재사용 가능한 프롬프트 템플릿. 제어 주체는 user.

MCP는 이보다 더 많은 primitive를 정의하지만, 이 문서는 본 프로젝트가 실제로 사용하는 tools만 기술한다

## 3. UCP (Universal Commerce Protocol)
Google이 Shopify, Target, Walmart 등과 공동 개발하여 2026년 1월 공개한 오픈 프로토콜.
A2A·AP2·MCP와 호환되도록 설계됨.
아래 항목은 Google의 공식 분류와 정의를 기술한 것임.

### 3.1. Capabilities (핵심 기능)

**상품 발견 (discovery)**
- 가맹점이 선언파일(manifest)로 기능(capability)을 노출한다. 
- 에이전트가 이를 조회해 지원 서비스·기능(capability) 목록을 파악한다.

**체크아웃 (checkout)**
- 상품·수량, 구매자 정보, 결제 수단, 합계 계산을 하나의 세션 단위로 생성한다. 
- 결제 실행(AP2 mandate로 사용자 동의 검증)까지 이 세션 안에서 처리된다.

**구매 후 관리 (order management)**
- 기능(capability)이 추가로 존재하나, 체크아웃(checkout)과의 확장 관계는 공개 자료에 명시되지 않음.

### 3.2. Extensions (확장 기능)

**할인·이행 적용 (discount / fulfillment)**
- 이미 생성된 체크아웃 세션에 할인 적용이나 배송·이행 처리를 덧붙인다. 
- 독립된 별도 세션을 만들지 않고 체크아웃(checkout)을 확장(extends)하는 방식으로 동작한다.

### 3.3. Sub-protocols (하위 프로토콜)

**ECP (Embedded Checkout Protocol)**
UCP의 Embedded Protocol(EP) 전송 방식(transport binding) 중 체크아웃에 특화된 구현체다. 호스트 애플리케이션이 가맹점의 체크아웃 UI를 자체 화면 안에 임베드하고, 구매자가 체크아웃을 진행하는 동안 발생하는 이벤트를 수신하며, 주소·결제수단 선택 같은 주요 동작을 자신의 네이티브 UI로 위임(delegate)할 수 있게 한다. human-in-the-loop이 필요한 체크아웃 시나리오(예: 사용자가 직접 결제수단을 고르는 경우)를 처리하는 데 쓰인다.

## 4. AP2 (Agent Payments Protocol)
Google이 60개 이상의 결제·기술 기업과 공동 개발하여 2025년 9월 공개한 오픈 표준(현재 FIDO Alliance에 기증되어 관리됨).
AI 에이전트가 사용자를 대신해 안전하게 결제를 개시·실행할 수 있도록 하는 프로토콜.
A2A·MCP의 확장으로 사용 가능하며, 결제 수단(카드·계좌이체·스테이블코인 등)에 대해 payment-agnostic함.
아래 항목은 Google의 공식 분류와 정의를 기술한 것임.

### 4.1. Roles (역할)

**Merchant Agent**
가맹점을 대신해 결제를 수락하는 에이전트다.

**User Agent**
사용자를 대신해 결제를 개시하는 에이전트다.

**Payment Rail**
실제 결제를 정산하는 결제망(네트워크)이다.

### 4.2. Mandates (핵심 개념)
Mandate는 암호학적으로 서명된 검증 가능 자격증명(Verifiable Credential)으로, 사용자 의도부터 최종 결제 승인까지의 흐름을 증명한다.

**Intent Mandate**
사용자의 최초 요청·의도를 나타낸다.

**Cart Mandate**
장바구니 내용이 사용자 의도와 일치함을 서명으로 확인한다.

**Payment Mandate**
사용자의 최종 결제 승인을 서명으로 증명한다.

## 5. 마이데이터

### 5.1. 본인신용정보관리업 (마이데이터)
개인이 여러 금융회사에 흩어진 신용정보를 하나의 서비스에서 통합 조회할 수 있게 하는 표준 API 기반 데이터 연동 체계. 본 프로젝트에서는 사용자의 카드 정보를 한 곳에서 모아 혜택을 비교·추천하는 데 사용.

### 5.2. 정보제공자 / 정보수신자 구조
데이터 연동 구조상 카드사는 결제내역·카드상세·실적·혜택 데이터를 제공하는 쪽(정보제공자)이고, 우리 서비스는 이를 받아 사용자에게 통합해 보여주는 쪽(정보수신자). 카드사별로 표준화된 API 규격을 통해 데이터를 받아온다.

### 5.3. 전송요구 (사용자 동의 절차)
사용자가 자신의 카드 정보를 우리 서비스로 가져오도록 동의·요청하는 절차. 단순 로그인이 아니라 별도의 동의 플로우로 설계됨.
