# 검색과 장바구니 지연 측정 (Task 499)

현재는 측정 준비 단계다. 실제 ChatGPT/Claude 표본 수집 전이며 지연 원인이나 개선 수치는 확정하지 않는다.
기존 `MCP timing` 로그를 활용하므로 1차 수집에 MCP 재배포나 로그 초기화가 필요하지 않다.

## 구간과 한계

| 구간 | 근거 | 현재 구분 가능 여부 |
| --- | --- | --- |
| 요청 전송→첫 안내/질문 | 사용자 화면 녹화 또는 스톱워치 | 사용자 기록 필요 |
| 요청 전송→최종 결과 표시 | 사용자 화면 | 사용자 기록 필요 |
| 각 MCP 도구 실행 | requestId, tool, error, elapsedMs | 기존 서버 로그 |
| 서비스 토큰 준비 | 같은 requestId의 service_token | 기존 서버 로그 |
| MCP→Core 응답 해석 완료 | 같은 requestId의 core_http | 네트워크·Core·판매처 작업을 포함한 왕복 |
| Core 처리와 판매처 대기 각각 | Core/판매처 span | 현 로그만으로 분리 불가, 1차 결과에 따라 추가 계측 |
| 모델 추론/호스트 스케줄링/화면 렌더링 각각 | 호스트 계측 | 서버 로그로 확정 불가 |
| 응답 크기·동일 검색 중복 여부 | 추가 계측 또는 호스트 도구 실행 내역 | 도구 호출 횟수만으로 확정 불가 |

도구 전체 시간에는 하위 Core 호출이 포함된다. 둘을 더하지 않는다. 병렬 도구의 시간 합계는
실제 대기시간보다 클 수 있으므로 전체 대기와 비교할 때 시간 구간의 합집합을 사용한다.
전체 시간에서 MCP 구간을 뺀 값도 네트워크·호스트·사용자 응답 대기 등을 포함하며 모델 추론 시간이 아니다.
도구 종료 로그가 누락된 경우와 여러 사용자가 동시에 테스트하는 경우에는 분석 범위를 먼저 확인한다.

## 첫 수집 — EC2에서 실행

로그를 지우거나 서비스를 재시작하지 않는다. 아래 명령을 실행한 뒤 호스트에서 요청을 한 번 보내고,
최종 결과가 표시되면 터미널에서 Ctrl+C를 누른다. 요청 도중에는 멈추지 않는다.

```bash
cd /opt/copenhagen
umask 077
QA_LOG="$HOME/copenhagen-qa499-$(date -u +%Y%m%dT%H%M%SZ).log"
printf '기록 파일: %s\n시작 UTC: ' "$QA_LOG"
date -u +%Y-%m-%dT%H:%M:%SZ
docker compose --env-file .env \
  -f docker-compose.yml -f infra/docker/https.override.yml \
  logs --follow --since 0s --timestamps --no-color mcp-server \
  | grep --line-buffered 'MCP timing:' | tee "$QA_LOG"
```

Ctrl+C 후 같은 터미널에서 `cat "$QA_LOG"`로 확인한다. 파일이 비어 있으면 성공 표본이 아니다.
도구를 실제로 호출했는지, 해당 MCP 컨테이너에 timing 로그가 있는지 확인한다.
기록 공유는 timing 로그만 전달하며 환경변수·토큰·쿠키·개인키는 포함하지 않는다.

첫 시나리오는 새 대화에서 **“2명이 먹을 삼겹살, 쌈채소, 마늘, 고추, 쌈장을 찾아줘.
장바구니에는 담지 말아줘.”**로 고정한다. 불명확한 인원 질문의 시간을 섞지 않기 위한 기준 요청이다.
다른 사람이 동시에 사용했다면 표시하고, 가능하면 해당 도구 결과의 diagnostics requestId로 매칭한다.

함께 기록할 정보:

```text
run_id: chatgpt-ingredients-01
호스트 / 화면에 표시된 모델:
서버 이미지 태그 / 배포 시각:
조건: 첫 요청(first-observed) / 동일 조건 반복(warm) / 알 수 없음
전송 시각(시간대 포함):
첫 안내까지(초):
최종 결과 표시까지(초):
중간 질문·권한 승인·재연결 대기(초):
호스트가 보여준 도구 이름·호출 횟수 / 웹 검색 여부:
다른 사용자 동시 사용 여부:
결과: 성공 / 일부 실패 / 실패
```

첫 요청을 곧바로 cold-cache라고 부르지 않는다. 서비스 토큰·검색 캐시 상태를 모르면
`first-observed`로 남긴다. 운영 캐시 제거·서버 재시작으로 cold를 강제로 만들지 않는다.

## 분석

분석기가 있는 로컬 작업 디렉터리에서 수집 파일을 지정한다. 외부 Python 패키지는 필요 없다.

```bash
python3 scripts/analyze-mcp-timing.py /path/to/qa499.log --observed-seconds 80
```

80은 예시이며 실제 측정값으로 바꾼다. 도구별 호출 수·오류·p50/p95,
요청별 Core 호출 수·누적 왕복·토큰 준비 시간을 출력한다. 원본 로그 본문은 출력하지 않는다.
`mcp_busy_union_ms`는 MCP 도구 실행 구간의 합집합이고 하위 타이머와 더하지 않는다.
`outside_mcp_or_unattributed_ms`는 미분류 구간이다. 서로 다른 실행 파일을 합쳐 전체 대기와 비교하지 않는다.
원본 로그의 타임스탬프가 없거나 요청 종료가 누락되면 이 값은 null이다.

## 반복 QA와 완료 기준

1. ChatGPT에서 1회 수집하여 계측 연결부터 확인한다.
2. 같은 조건으로 Claude에서도 수집한다. 호스트 모델과 권한 확인 횟수를 기록한다.
3. 단일 상품, 5종 재료, 구매내역 기반 재구매 탐색, 장바구니 수량 변경을 각각 비교한다.
   수량 변경은 사용자가 선택한 테스트 상품에서만 실행하며 결제 요청·실결제를 하지 않는다.
4. 시나리오·호스트·캐시 조건별 표본을 분리한다. 예비 표본은 3회, 안정적인 p95 비교는
   각 조건 최소 20회로 확장한다. 작은 표본의 p95는 참고값임을 명시한다.
5. 전체 시간은 사용자 기록의 실행별 표본으로 집계한다. 분석기의 도구별 백분위와 혼동하지 않는다.
6. Core 왕복이 주요 지연이면 Core/판매처 span을 추가한다. 호스트 쪽 비중이 크면 웹 검색,
   도구 왕복 수, 중간 설명, 불필요한 재조회와 응답 크기를 추가 확인한다.

Task 499는 실제 표본·호스트 비교·병목 보고까지 확보한 후 완료한다.
측정 스크립트 테스트 통과만으로 완료 처리하거나 성능 개선 달성을 주장하지 않는다.
