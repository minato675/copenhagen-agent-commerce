# 관리자 응답시간 측정

## 배포 설정

MCP 이미지와 Core 이미지(새 로그인 로고)를 배포합니다. EC2 `/opt/copenhagen/.env`에 다음을 설정합니다.

```dotenv
MCP_DIAGNOSTICS_ENABLED=true
MCP_DIAGNOSTICS_ADMIN_USER_REFS=<승인한 관리자 계정의 public_id>
```

관리자 ID는 서버에서 조회한 `users.public_id`입니다. 사용자 입력이나 로그인명으로 권한을 판단하지 않습니다.
이는 진단 기능만 허용하며 계정 관리·타 사용자 구매내역 접근 등의 전역 관리자 역할을 부여하지 않습니다.
여러 ID는 쉼표로 구분하며 기본값은 비활성화입니다. DB 권한 데이터를 수정할 필요는 없습니다.

```bash
cd /opt/copenhagen
docker compose --env-file .env -f docker-compose.yml -f infra/docker/https.override.yml \
  up -d --no-deps --force-recreate mcp-server core-service
```

이미지 태그가 변경된 코드로 빌드되었는지 먼저 확인합니다. 이후 플러그인의 도구 목록을 새로고침합니다.

## 사용

1. 관리자 계정으로 연결한 대화에서 `응답시간 체크해줘`를 요청합니다.
2. `start_response_timing`이 30분짜리 측정 세션을 반환합니다.
3. 모델은 이 대화의 이후 도구에 `diagnosticSessionId`를 전달합니다. 인자는 서버에서 제거되어 업무 API에 전달되지 않습니다.
4. 작업 마지막에 `get_response_timing`을 호출해 새 기록을 요약합니다.
5. `측정 종료해줘`는 `stop_response_timing`으로 최종 기록을 반환한 뒤 삭제합니다.

세션 ID가 생략된 요청과 플러그인을 호출하지 않는 일반 대화는 기록되지 않습니다. 모델의 세션 전달·보고 호출은
실제 ChatGPT/Claude에서 QA해야 하며 최종 글자 출력 직후 실행을 보장하지 않습니다. 누락 시 `측정 결과 보여줘`로 조회합니다.
다른 대화에는 별도 세션을 사용합니다. 같은 계정이 세션 ID를 복사하면 공유할 수 있으므로 호스트 대화 ID에 의한 강제 격리는 아닙니다.

## 측정 범위 및 해석

- `elapsedMs`: 인증·입력 검증 이후 업무 handler의 경과 시간. GPT 추론·출력 시간이나 HTTP 전체 왕복 시간이 아닙니다.
- `stages`: 동일 실행 스레드의 서비스 토큰 발급(`service_token`), Core HTTP 요청(`core_http`) 경과 시간.
- 하위 시간은 handler 시간에 포함됩니다. 전체 시간과 더하지 않습니다. 병렬 작업 시간도 단순 합산하지 않습니다.
- Core 내부 DB·쇼핑몰 호출은 별도 계측 전까지 구분할 수 없습니다. Core HTTP가 느리면 기존 requestId 서버 로그로 추가 조사합니다.
- 호출 간 공백에는 호스트·네트워크·사용자 대기가 포함됩니다. GPT 추론 시간으로 단정하지 않습니다.
- 오류는 `failed`로 표시하며 요청 인자·상품·토큰·예외 원문은 수집하지 않습니다.

기록은 프로세스 메모리에 보관합니다. 서버 재시작·재연결 시 새 세션을 시작해야 하며 여러 MCP 인스턴스에서는
공유 저장소가 필요합니다. 최대 100세션, 세션별 200호출, 호출별 100하위 구간으로 제한합니다.
`truncated=true`이면 전체 기록이 아니므로 새 세션으로 다시 측정합니다.

## 검증

관리자/비관리자, 다른 연결, 세션별 분리, 만료, 종료, 기록 한도, 예외 원문 비노출, schema 전달 및
진단 인자의 업무 API 전달 방지를 자동 검증합니다. 배포 후 관리자 시작 → 상품 검색 → 결과 조회 → 종료와
일반 계정의 거부를 확인합니다. 운영 계정 설정은 배포 환경에서 적용해야 하며 소스만 push해서 활성화되지 않습니다.
