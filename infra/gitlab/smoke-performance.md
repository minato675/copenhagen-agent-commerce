# 배포 스모크 실행 시간 — S15P21A207-399

## 목표

기존 배포 검증을 유지하면서 `deploy-smoke` Job 실행 시간을 300초 이내로 줄입니다.
Runner 대기 시간과 전체 pipeline 경과 시간은 별도로 기록합니다.
빌드를 다른 Job으로 이동한 시간은 성능 개선으로 계산하지 않습니다.

## 유지할 검증

- 고정 기준 SHA와 후보 SHA 검증
- 빈 DB에서 전체 스택 신규 설치
- 서비스별 순차 업그레이드와 각 단계의 HTTP·데이터 보존 검사
- Nginx 공개 경로와 내부 경로 차단
- 실패 이미지 배포 후 이전 이미지·환경 복구
- 실패 진단, 비밀값 마스킹 및 임시 자원 정리

## 검증 계획

1. 중복 빌드, HTTP 실행과 기동 대기의 소요 시간을 기록합니다.
2. 변경에 맞는 회귀 테스트, shell 문법과 ShellCheck를 실행합니다.
3. 실제 GitLab 스모크 성공과 Job 소요 시간을 확인합니다.
4. 실행 SHA, Runner, cache 상태와 단계별 소요 시간을 이 문서에 기록합니다.

## 구현

- `smoke-dockerfiles.py`는 동일한 표준 소스 builder의 `bootJar` 태스크를 한 Gradle
  실행으로 묶습니다. 첫 서비스의 빌드 계층을 나머지 서비스가 공유합니다.
  기준 버전에도 같은 조건으로 적용합니다. 런타임 단계는 바이트 단위로 보존하며
  표준 builder와 다른 파일은 원본 그대로 빌드합니다.
- 다섯 이미지는 Buildx Bake 한 번으로 빌드해 동일한 계층과 레지스트리 조회를 공유합니다.
- HTTP 요청 90회는 Compose의 전용 curl 컨테이너를 재사용합니다. 전체 HTTP 검사
  9회와 서비스 내부에서 실행하는 의존 서비스 요청, DB 검사 18회는 유지합니다.
- 스모크에만 앱 health 주기 2초·시작 주기 1초, DB·Redis 주기 1초를 적용합니다.
  health 명령·의존 관계·앱 시작 유예 기간을 유지하고 재시도 횟수를 늘려 기존의
  앱 120초, DB 60초 실패 대기 구간을 보존합니다. 실제 timeout은 probe 실행 시간도
  포함하므로 이 곱만으로 정확한 최대 소요 시간을 계산하지 않습니다.
- `result.log`에 준비·빌드·기동·서비스별 교체·복구·정리와 총 실행 시간을 남깁니다.
- GitLab cache에는 Gradle `caches/`와 `wrapper/`만 저장합니다. 전용 Dockerfile로
  매번 새 DinD의 기존 `/root/.gradle` cache mount에 넣고 검증 완료 후 내보냅니다.
  브랜치별 키와 develop fallback을 사용합니다. 기준 버전과 로컬 이미지는 해당
  소스에서 빌드하며, CI 후보는 같은 pipeline에서 검증한 JAR를 패키징합니다.
  캐시가 없는 첫 실행은 다운로드 비용이 추가됩니다.
- JDK·JRE·Nginx·DB·Redis·curl 기반 이미지는 별도의 `images.tar`로 같은 GitLab
  캐시에 보관합니다. 복원 후 원격 태그를 다시 확인하고 변경된 계층은 내려받습니다.
  후보 앱 이미지는 이 tar에 포함하지 않습니다. DB 데이터와 설정·비밀값도 포함하지 않습니다.
- CI의 후보·기준 소스를 모두 `git archive`로 만들어 체크아웃 파일 권한 차이가
  동일한 backend의 Docker 빌드 계층 재사용을 방해하지 않게 합니다. 로컬 실행은
  기존처럼 현재 작업 디렉터리의 소스를 빌드합니다.
- 스모크 앱과 표준 Temurin 21 공유 빌드에 `-XX:TieredStopAtLevel=1`을 적용해 JVM 기동
  비용을 줄입니다. 애플리케이션 초기화와 bytecode 검증은 그대로 실행합니다.
  장시간 실행 시 JIT 최적화 수준은 운영 환경과 다르므로 처리량 측정에는 쓰지 않습니다.
  참고: [Spring의 JVM 기동 최적화 설명](https://spring.io/blog/2018/12/12/how-fast-is-spring/).

## 검증 상태

아래 시간은 `S15P21A207-392`의 CI JAR 재사용 작업과 통합하기 전 측정값입니다.
병합 준비 중 최신 develop을 반영해 CI 후보의 artifact 재사용과 출처 검증을 유지하고,
기준·로컬 소스 빌드의 worker 옵션과 공통 빌드를 함께 적용했습니다. 스모크 전용 파일
변경에도 다섯 JAR가 준비되도록 Job 선택 규칙을 맞췄습니다. 통합 커밋은 MR pipeline에서
다시 검증하며 기존 측정값을 통합 후 성능으로 간주하지 않습니다.

- 회귀 테스트 37개, Bash 문법, ShellCheck 0.10.0, diff 검사 통과.
- `./gradlew checkstyleMain checkstyleTest build --no-daemon` 통과.
  총 1,117개 중 실패 0개, Core 외부 DB 환경변수 조건에 따른 skip 81개.
- 실제 Docker에서 Gradle 캐시를 새 mount로 복원하고 임시 소스 복사본을 변경해
  재빌드 확인. 변경한 PG 모듈은 다시 컴파일, 나머지 모듈은 캐시 재사용,
  Gradle 7초 성공. 애플리케이션 이미지를 이전 결과로 대체하지 않음.
- 최종 구현 `ad9cea87`은 [GitLab Job #564141](https://lab.ssafy.com/s15-fintech-finance-sub1/S15P21A207/-/jobs/564141)에서
  전체 통과했습니다. EC2의 캐시 없는 첫 실행은 Job 580초, script 535초입니다.
- 같은 커밋을 완전히 새 Docker 28.5.2 daemon에서 실행하고 저장된 Gradle·기반 이미지
  캐시만 복원한 로컬 검증은 전체 120초에 통과했습니다. Gradle 빌드는 7초였습니다.
- 실제 GitLab에서 300초 이내 완료는 입증하지 않았습니다. 현재 구현과 검증 결과를
  정리하고 추가 최적화·반복 측정은 종료했습니다.

## 측정 조건

Job 시간에는 준비, 캐시 복원·저장, 스모크와 정리, artifact 업로드를 포함합니다.
`result.log`의 script 시간은 Runner의 외부 준비·캐시 압축 시간을 포함하지 않습니다.
캐시가 없는 첫 실행, Runner 변경, 기반 이미지·의존성 갱신 시 다운로드 비용이 추가됩니다.
현재 Runner cache는 로컬 저장소이므로 다른 Runner의 캐시를 자동으로 공유하지 않습니다.
따라서 느린 네트워크를 가진 Runner의 최초 실행까지 5분을 보장하지 않습니다.

초기 두 CI 실행은 Runner가 달라 직접 개선율을 계산하지 않습니다. 두 번째 실행의 후보 빌드는
374초, 신규 설치는 248초였고, 기준 빌드 8초·기준 기동 16초·서비스 교체 각각 5~6초였습니다.
캐시 추가는 반복 다운로드가 이 짧은 기능 검증을 지연시키는 문제를 해결하기 위한 것입니다.

최종 EC2 script는 준비 8초, 후보 빌드 218초, 신규 설치 77초, 기준 빌드 2초,
기준 기동 65초, 서비스 교체 합계 97초, 최종 HTTP 5초, 복구 21초,
Gradle 캐시 내보내기 14초, 기반 이미지 저장 24초, 정리 4초였습니다.
새 로컬 daemon에서는 같은 항목이 각각 12·20·22·1·19·28·2·9·3·2·2초였습니다.
Runner 성능·부하·네트워크·캐시 조건이 다르므로 두 실행의 차이를 코드 개선율로 계산하지 않습니다.
