## 1. 프로젝트 개요

서비스 URL: `https://j15a207.p.ssafy.io`

| 디렉터리 | 내용 |
| --- | --- |
| `backend/` | Core, MCP, Pay, Merchant Mock, PG Mock |
| `mobile/` | Android 앱 (Kotlin + Jetpack Compose) |
| `ai/` | FDS(이상거래 탐지) 평가 모듈 |
| `infra/` | Docker, Nginx, GitLab CI/CD 및 배포 설정 |

사용자의 자연어 구매 요청을 AI Agent가 해석하고 MCP Tool을 통해 상품 탐색, 장바구니 구성 및 Checkout 생성 등의 구매 절차를 수행한다. 결제 전 Core가 상품, 금액, 배송 정보 등 주문 내용을 다시 검증하며, 사용자가 모바일 앱에서 PIN 또는 생체인증으로 최종 승인한 경우에만 결제가 진행된다.

| 구성 요소 | 기술 / 역할 | 주요 책임 |
| --- | --- | --- |
| Mobile App | Kotlin + Jetpack Compose | 로그인, 배송지·카드 관리, 승인 대기 확인, PIN·생체인증, 주문 이력 |
| Agent | LLM / ChatGPT Plugin | 자연어 요청 해석, MCP Tool 호출, 사용자와의 구매 대화 |
| MCP Server | MCP | Agent의 Tool 요청을 백엔드 기능 호출로 연결하는 진입점 |
| Core | Spring Boot / Java | 인증, 장바구니, Checkout Snapshot, 주문 검증, 결제 실행 조정, 주문 이력 |
| Pay | Spring Boot / Java | 결제 승인 세션, PIN·생체 승인, Credential 발급, PG 연동 |
| Merchant Mock | Spring Boot / Java | 상품 조회, Checkout, 주문 생성 등 판매처 기능 제공 |

## 3. 서비스 구성과 포트

애플리케이션 서비스는 Docker Compose 내부 네트워크에서 서비스명으로 통신하며, 외부 요청은 Nginx를 통해 전달됩니다.

| Compose 서비스 | 역할 | 소유 DB |
| --- | --- | --- |
| `nginx` | 외부 요청 진입점 및 Reverse Proxy | - |
| `mcp-server` | Agent의 MCP Tool 요청을 백엔드 기능 호출로 연결 | - |
| `core-service` | 사용자 인증, OAuth, 상품·장바구니·구매 및 주문 흐름 관리 | `core-db` |
| `pay-service` | 결제수단, 사용자 승인, Credential, 결제 처리 및 푸시 알림 | `pay-db` |
| `ucp-merchant-mock` | 가상 판매처 3곳의 상품·Checkout·주문 기능 제공 | `merchant-db` |
| `pg-mock` | PG 결제 승인 및 결과 시뮬레이션 | - |
| `core-db` / `pay-db` / `merchant-db` | PostgreSQL 17 | - |
| `redis` | Redis 7.4 | - |

외부에는 Nginx만 공개합니다.

| 호스트 포트 | 용도 |
| --- | --- |
| `NGINX_PORT` | HTTP (`8080` 로컬, `80` EC2) |
| `NGINX_HTTPS_PORT` | HTTPS (`443`) |

EC2에서는 HTTP 요청을 HTTPS로 리다이렉트합니다.

## 4. 로컬 실행 (Docker Compose)

> 로컬 Docker Compose 실행은 Docker·DB·서비스 간 통신·API 검증용입니다. localhost는 실제 ChatGPT 플러그인
> OAuth 및 Checkout E2E 연결 대상이 아니며, 해당 검증은 공개 HTTPS EC2 환경에서 수행합니다.

준비물은 Docker Engine과 Docker Compose v2입니다. 저장소 루트에서 실행합니다.

```bash
git clone <GitLab 저장소 URL> S15P21A207
cd S15P21A207
docker compose up --build -d
docker compose ps            # 애플리케이션 컨테이너가 모두 healthy인지 확인
```

- 로컬 기본 주소는 `http://localhost:8080`입니다.
- 별도 `.env` 없이도 기동됩니다. `docker-compose.yml`에 **개발 전용 기본값**(DB 비밀번호, PII 암호화 키, 로그인 JWT 키)이 들어 있기 때문입니다.
- 첫 기동 때 Flyway가 스키마를 만들고 시드 데이터를 넣습니다. Merchant Mock은 약 10만 건 카탈로그(`catalog/pool.json.gz`)를 적재하므로 시간이 걸립니다. 줄이려면 `MERCHANT_CATALOG_POOL_LIMIT=<건수>`를 지정합니다.

상태 확인:

```bash
docker compose exec core-service wget -qO- http://localhost:8080/actuator/health
docker compose logs -f core-service
```

종료:

```bash
docker compose down            # DB 데이터 보존
docker compose down --volumes  # DB·Redis 데이터까지 삭제(초기화)
```

> 로컬 기본값만으로는 MCP 인증 프로필(`core-integration`), 푸시 알림, Core→Pay 서비스 토큰이 꺼져 있습니다. 전체 구매 흐름을 확인하려면 5장의 환경변수를 설정해야 합니다.

## 5. 환경변수

EC2 운영 환경은 infra/docker/ec2.env.example을 템플릿으로 사용해 배포 디렉터리의 .env를 구성합니다.

```bash
cp infra/docker/ec2.env.example .env
chmod 600 .env
```

세부 옵션은 infra/docker/ec2.env.example과 각 서비스 설정 파일을 기준으로 합니다.

> `ec2.env.example`에는 아래 표의 운영 필수값 중 일부가 없거나 주석 처리되어 있습니다. 복사 후 다음 값을 `.env`에 직접 추가합니다. 값이 없으면 `docker-compose.yml`의 개발용 기본값이 사용되거나 서비스 간 호출이 `401`로 실패합니다.
>
> - Core: `CORE_PII_ENC_KEY`, `CORE_PII_HASH_PEPPER`, `CORE_AUTH_JWT_PRIVATE_KEY`, `CORE_PAY_SERVICE_TOKEN`
> - Pay: `PAY_AUTH_CORE_SERVICE_TOKENS_JSON`, `PAY_AUTH_MERCHANT_SERVICE_TOKENS_JSON`, `PAY_AUTH_JWT_ENABLED`, `PAY_AUTH_JWT_ISSUER`, `PAY_AUTH_JWT_JWK_SET_JSON` (템플릿에서는 주석 처리됨)
>
> 템플릿의 `CHANGE_ME` 값도 모두 실제 값으로 바꿉니다. 하나라도 남아 있으면 `scripts/bootstrap-dev-infra.sh`가 실패합니다.

주요 계정 및 프로퍼티 정의 파일은 다음과 같습니다.

| 구분 | 파일 | 내용 |
| --- | --- | --- |
| Compose 실행 설정 | `docker-compose.yml` | 컨테이너별 DB 접속값, 서비스 URL, 환경변수 주입 및 개발 기본값 |
| EC2 환경변수 템플릿 | `infra/docker/ec2.env.example` | EC2 `.env`에 작성할 DB 계정·포트·MCP·Worker·FCM 설정 예시 |
| Core 설정 | `backend/apps/core-service/src/main/resources/application.yml` | Core DB, PII, JWT, OAuth, Pay·Merchant 연동 속성 |
| MCP 설정 | `backend/apps/mcp-server/src/main/resources/application.yml` | MCP 기본 서비스·보안 속성 |
| MCP 운영 프로필 | `backend/apps/mcp-server/src/main/resources/application-core-integration.yml` | Core 연동 운영 프로필 속성 |
| Pay 설정 | `backend/apps/pay-service/src/main/resources/application.yml` | Pay DB, 인증, 승인·알림·PG 연동 속성 |
| Merchant 설정 | `backend/mocks/ucp-merchant-mock/src/main/resources/application.yml` | Merchant DB, 서비스 포트, 판매처·결제 연동 속성 |
| PG Mock 설정 | `backend/mocks/pg-mock/src/main/resources/application.yml` | PG Mock 결제 결과·응답 지연 설정 |
| 계정·ERD 스키마 | 9장 데이터베이스 표의 각 `db/migration` 디렉터리 | Flyway DDL과 계정·도메인·시드 데이터 정의 |

### 5.3 MCP Server

| 변수 | 운영 필수 | 설명 |
| --- | --- | --- |
| `MCP_SPRING_PROFILES_ACTIVE` | O | 반드시 `core-integration`으로 설정. 템플릿 기본값은 빈 값이며, 비워 두면 MCP 인증과 쇼핑 도구가 비활성화됨 |
| `MCP_AUTH_RESOURCE` | O | MCP Resource URI. `https://j15a207.p.ssafy.io/mcp` |
| `MCP_AUTH_ISSUER` | O | OAuth issuer. `https://j15a207.p.ssafy.io` |
| `MCP_AUTH_JWKS_URI` | O | OAuth 공개키 조회 URI. `https://j15a207.p.ssafy.io/.well-known/jwks.json` |

`MCP_ALLOWED_HOSTS`, `MCP_ALLOWED_ORIGINS`, 진단 관련 환경변수 등은 기본 설정을 사용할 수 있으며 필요 시 `ec2.env.example`에서 변경합니다.

| `MERCHANT_CATALOG_POOL_LIMIT` | - | 상품 데이터 적재 제한. `0`이면 전체 데이터 사용 |

`PAY_MERCHANT_TOKEN`, `PG_MOCK_LOOKUP_OUTCOME`, `PG_MOCK_RESPONSE_DELAY_MILLIS` 등은 개발·테스트용 설정이므로 일반적인 운영 배포에서는 기본값을 사용합니다.

### 5.6 서비스 간 설정 일치 조건

아래 항목은 각 서비스에 설정된 값이 서로 일치해야 정상적으로 연동됩니다.

- `CORE_PAY_SERVICE_TOKEN`\
  ↔ `PAY_AUTH_CORE_SERVICE_TOKENS_JSON`의 `core-service` 값

- `PAY_AUTH_JWT_JWK_SET_JSON`의 `kid`\
  ↔ `A207` (Core 로그인 JWT 키 식별자 고정값)

- `PAY_AUTH_JWT_ISSUER` / `PAY_AUTH_JWT_AUDIENCE`\
  ↔ Core 로그인 JWT의 `copenhagen-core` / `pay-service`

- `CORE_AUTH_JWT_PRIVATE_KEY`\
  ↔ `PAY_AUTH_JWT_JWK_SET_JSON`에 등록된 공개키

- `AGENT_OAUTH_ISSUER`\
  ↔ `MCP_AUTH_ISSUER`

- `AGENT_OAUTH_MCP_AUDIENCE`\
  ↔ `MCP_AUTH_RESOURCE`

- `PAY_MERCHANT_TOKENS_JSON`\
  ↔ `PAY_AUTH_MERCHANT_SERVICE_TOKENS_JSON`

값이 불일치하면 서비스 기동 자체는 성공하더라도 내부 API 호출, OAuth 인증 또는 결제 승인 과정에서 `401 Unauthorized` 등의 오류가 발생할 수 있습니다.

### 5.7 키 및 토큰

운영 환경에서는 다음 형식의 키 및 토큰을 사용합니다.

- `CORE_AUTH_JWT_PRIVATE_KEY`: P-256 PKCS#8 DER Base64URL (`+`, `/` 대신 `-`, `_` 사용. 일반 Base64 값은 기동 실패 가능)
- `AGENT_OAUTH_JWT_PRIVATE_KEY`: P-256 PKCS#8 DER Base64URL
- `CORE_PII_ENC_KEY`: 32바이트 Base64
- 서비스 간 인증 토큰: 임의의 충분히 긴 난수값

실제 키와 토큰은 `.env` 등 운영 환경에서 관리하며 저장소에는 포함하지 않습니다.

### 6.2 HTTPS 인증서 준비 및 갱신

개발 EC2는 `infra/docker/https.override.yml`과 `infra/nginx/nginx.https.conf`를 사용합니다. `.env`에는 `NGINX_PORT=80`을 설정하며 HTTPS 포트는 `NGINX_HTTPS_PORT`의 기본값 `443`을 사용합니다.

인증서는 6.3의 서비스 기동 전에 Let's Encrypt로 발급해 아래 표의 경로에 준비해야 합니다. `nginx.https.conf`는 인증서 파일이 있어야 기동됩니다.

아래 갱신 타이머(`copenhagen-certbot-renew.timer`)와 스크립트(`/usr/local/sbin/copenhagen-renew-tls`)는 서버에서 직접 관리하는 파일이며 저장소에는 포함되어 있지 않습니다.

| 항목 | 값 / 절차 |
| --- | --- |
| 대상 도메인 | `j15a207.p.ssafy.io` |
| 인증서 파일 | `/etc/letsencrypt/live/j15a207.p.ssafy.io/fullchain.pem` |
| 개인키 파일 | `/etc/letsencrypt/live/j15a207.p.ssafy.io/privkey.pem` |
| ACME HTTP-01 경로 | `/var/lib/letsencrypt/www/.well-known/acme-challenge/` |
| HTTPS Nginx 적용 | `sh scripts/deploy-dev-nginx.sh` |
| 갱신 상태 확인 | `sudo systemctl status copenhagen-certbot-renew.timer` |
| 갱신 dry-run | `sudo /usr/local/sbin/copenhagen-renew-tls --dry-run --run-deploy-hooks` |

인증서와 개인키는 Git, CI/CD 변수, 빌드 산출물에 포함하지 않습니다.

인증서가 없거나 잘못된 경우 HTTPS Nginx 적용 스크립트는 기존 Nginx 컨테이너를 교체하지 않고 실패합니다.

### 6.4 MCP-Core 서비스 인증 설정 (`core-integration` 사용 시)

MCP-Core 연동에는 서비스 인증키가 필요합니다.

1. EC2의 저장소 외부 비밀 디렉터리에 MCP 서비스용 개인키 파일 `client.jwk`를 배치합니다.
2. `.env`에 아래 값을 설정합니다.

   ```dotenv
   MCP_SPRING_PROFILES_ACTIVE=core-integration
   MCP_SECRETS_DIR=<client.jwk가 있는 디렉터리의 절대경로>
   ```

   Docker Compose가 해당 디렉터리를 MCP 컨테이너의 `/run/secrets/mcp`에 읽기 전용으로 연결합니다.

3. Core DB의 기존 `oauth_clients` 중 `client_id='copenhagen-mcp'` 행의 `client_jwks` 컬럼에, `client.jwk`와 대응하는 **공개 JWK**를 등록합니다.

개인키는 Git, `.env`, Core DB에 저장하지 않습니다. `core-integration`을 사용하지 않는 단순 기동에는 이 설정이 필요하지 않습니다.

다른 도메인에 배포할 경우 `.env`의 도메인 값과 함께 `infra/nginx/nginx.https.conf`, `infra/docker/https.override.yml`, `backend/apps/mcp-server/src/main/resources/application-*.yml`, `docker-compose.yml`의 `j15a207.p.ssafy.io`를 변경합니다.

## 9. 데이터베이스 (DB 덤프 포함)

- DB 3개(`core-db`, `pay-db`, `merchant-db`)는 서로 독립적이며, 각 서비스만 자기 DB에 접근합니다.
- 스키마와 시드는 애플리케이션 기동 시 **Flyway가 자동 적용**합니다. 따로 덤프를 import할 필요는 없습니다.
- 이미 적용된 migration 파일은 수정하지 않습니다. 변경이 필요하면 새 버전을 추가합니다.

| DB | migration 위치 | 주요 시드 |
| --- | --- | --- |
| core-db | `backend/apps/core-service/src/main/resources/db/migration` (V1~V22) | 판매처 3곳(V7, V8). OAuth 클라이언트 `chatgpt-plugin`·`copenhagen-mcp`(V10), ChatGPT 고정 콜백(V14), `claude-connector`(V20) |
| pay-db | `backend/apps/pay-service/src/main/resources/db/migration` (V1~V15) | 판매처 결제 계정(V12) |
| merchant-db | `backend/mocks/ucp-merchant-mock/src/main/resources/db/migration` (V1~V12) | 시드 상품 5건(V3). 기동 시 카탈로그 풀 약 10만 건 적재 |

- **사용자 계정은 시드되지 않습니다.** 앱에서 회원가입(`POST /api/core/v1/auth/signup`)을 하고 로그인합니다.
- DB 접속: `docker compose --env-file .env exec core-db psql -U <CORE_DB_USER> -d core-db`

최신 DB 덤프: 해당 없음(제공하지 않음). 각 DB는 애플리케이션 기동 시 Flyway migration과 저장소 시드로 재생성된다. 운영 사용자·결제 데이터는 포함하지 않는다.

## 13. 장애 대응 및 롤백

| 증상 | 주요 확인 항목 |
| --- | --- |
| 컨테이너 기동 실패 | 필수 환경변수, DB 연결, Flyway |
| Nginx `502` | 대상 서비스 상태 및 upstream |
| Core → Pay `401` | `CORE_PAY_SERVICE_TOKEN` ↔ Pay 토큰 매핑 |
| 앱 JWT 검증 실패 | Core 로그인 JWT 키 ↔ Pay JWK Set |
| MCP 인증 실패 | OAuth Issuer/Audience, `client.jwk`, Core OAuth Client 공개키 |
| 푸시 미수신 | FCM 설정, Pay Notification Worker |

배포 실패 시 CI/CD가 이전 이미지로 복구합니다. 수동 롤백은 이전 이미지 SHA를 기준으로 `scripts/deploy-dev-service.sh`를 사용합니다.
